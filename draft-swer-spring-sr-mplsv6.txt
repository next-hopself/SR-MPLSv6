  IPv4 Traffic over an IPv6-Only Segment Routing MPLS Underlay Network
                     draft-swer-spring-sr-mplsv6-00

Abstract

   Segment Routing over MPLS (SR-MPLS) can be deployed with an IPv6-only
   underlay and overlay.  In such deployments, the IGP links among
   Provider (P) and Provider Edge (PE) routers and the BGP sessions
   between PEs are IPv6-only.  The PEs' Prefix-SIDs are bound to IPv6
   prefixes, and IPv4 reachability is advertised with IPv6 next hops.
   This document refers to such deployments as SR-MPLSv6.

   This document specifies procedures for network layer awareness in the
   SR-MPLS data plane when IPv4 packets are carried using a Prefix-SID
   bound to an IPv6 prefix, without a service label.  The procedures
   address identification of the exposed payload after label removal and
   selection of the appropriate Explicit NULL label.  They cover
   penultimate hop popping, replacement with Explicit NULL, and ultimate
   hop popping, without requiring an additional label to identify IPv4
   packets.

1.  Introduction

   Segment Routing (SR) [RFC8402] over the MPLS data plane (SR-MPLS) is
   specified in [RFC8660].  SR-MPLS can be deployed with an IPv6-only
   underlay and overlay: the point-to-point IGP links are IPv6-only, the
   Prefix-SIDs that identify Provider Edge (PE) routers are attached to
   their IPv6 loopback addresses, and the BGP sessions between PEs are
   IPv6-only.  IPv4 routing is then enabled by advertising IPv4 Network
   Layer Reachability Information (NLRI) with IPv6 next hops [RFC8950].
   This document refers to such a deployment as SR-MPLSv6.

   The existing specifications do not define the label-processing
   procedures for SR-MPLSv6 when IPv4 packets are forwarded in the
   global routing table, i.e., without a service label.  Such packets
   carry the egress PE's Prefix-SID label, which is bound to an IPv6
   prefix.  A node that pops this label and exposes the payload, or
   replaces it with an Explicit NULL label, needs to identify the
   payload's network layer protocol.  Ambiguity in how that protocol is
   determined can lead to inconsistent forwarding behavior and
   interoperability problems.

   Some implementations use an approach similar to IPv6 Provider Edge
   (6PE) [RFC4798], in which BGP Labeled Unicast (BGP-LU) [RFC8277], or
   a similar mechanism, provides an additional bottom-of-stack label to
   identify IPv4 packets.  This label may be the IPv4 Explicit NULL
   label.  This approach increases the required label stack depth.  When
   the IPv4 Explicit NULL label is used, packets using this option
   arrive at the egress PE with that label, and therefore Penultimate
   Hop Popping is no longer an option to operators.

   Services that use a bottom-of-stack service label, including VRF-
   based services, are not affected by this ambiguity.  The service
   label determines the forwarding treatment at the egress PE according
   to the applicable service procedures, as described in Section 2.6.

   Section 3.3.2.1 of [RFC7439] identifies connecting IPv4 islands over
   an IPv6-only MPLS network as a major gap.
   [I-D.mishra-idr-v4-islands-v6-core-4pe] describes IPv4 Provider Edge
   (4PE) deployment options that address this gap, most of which use the
   approach described in Section 2.5 of this document.  For the two
   single-label options described in its Sections 8.4 and 8.5, that
   draft notes that deeper packet inspection may be required to identify
   the network layer protocol, but does not specify the inspection
   procedure.

   This document does not propose the same approach as
   [I-D.mishra-idr-v4-islands-v6-core-4pe].  It builds more directly on
   the approach described in Section 6.1 of [RFC8950] for
   interconnecting IPv4 islands over an IPv6 backbone, in which IPv4
   unicast routes are advertised without labels and with IPv6 next hops.
   The BGP next hop for such a route is the egress PE's IPv6 loopback
   address.  The ingress PE resolves this next hop to the Prefix-SID
   bound to that address.  No additional label is needed to identify
   IPv4 packets.

   This document specifies how SR-MPLSv6 nodes identify the payload's
   network layer protocol (IPv4 or IPv6) and use that information to
   select the appropriate forwarding treatment.  These network layer
   awareness procedures cover penultimate hop popping, selection of an
   Explicit NULL label, and ultimate hop popping.  Section 2 describes
   the problem in detail, Section 3 specifies procedures, Section 4
   specifies IPv6 TE Router ID requirements, and Section 5 illustrates
   the reference topologies they address.

1.2.  Terminology

   This document uses the terminology of [RFC3031], [RFC8402], and
   [RFC8660].  The IPv4 Explicit NULL label (0), the IPv6 Explicit NULL
   label (2), and the Implicit NULL label (3) are defined in Section 2.1
   of [RFC3032].  In addition, the following terms are used:

   SR-MPLSv6:  An SR-MPLS deployment in which the IGP underlay (point-
      to-point links and Prefix-SIDs) and the BGP overlay sessions
      between PEs are IPv6-only, and IPv4 reachability is provided by
      advertising IPv4 NLRI with IPv6 next hops [RFC8950].  SR-MPLSv6
      uses the MPLS data plane; it is distinct from Segment Routing over
      IPv6 (SRv6) [RFC8986].

   First hop:  The ingress PE, which receives a packet from a Customer
      Edge (CE) router, imposes the Prefix-SID label of the egress PE
      (the PUSH operation of [RFC8660]), and forwards the packet into
      the SR-MPLS domain.

   Transit node:  A Label Switching Router (LSR) that swaps the Prefix-
      SID label (the CONTINUE operation of [RFC8660]).

   Penultimate hop:  The upstream neighbor of the Prefix-SID originator
      along the path of the packet, i.e., the node immediately before
      the ultimate hop.

   Ultimate hop:  The egress PE, which originates the Prefix-SID
      attached to its IPv6 loopback address and is the BGP next hop of
      the IPv4 route.

   Payload address family:  The network layer protocol (IPv4 or IPv6) of
      the packet carried beneath the label stack.  This is distinct from
      the address family of the prefix to which the Prefix-SID is bound.

   PHP:  Penultimate Hop Popping [RFC3031].

   For the PE-to-PE forwarding paths described in this document, the
   first hop is the ingress PE, and the ultimate hop is the egress PE.
   These terms describe path positions and provider-edge roles,
   respectively.

2.  Problem Statement

   This section describes the payload-identification and forwarding
   issues that arise when IPv4 packets are carried over SR-MPLSv6
   without a service label.  It also describes existing workarounds and
   cases that are unaffected.

2.1.  Identifying the Network Layer Protocol of the Payload

   The MPLS label stack does not contain any field that explicitly
   identifies the network layer protocol of the payload.  Instead, the
   network layer protocol must be inferable from the value of the label
   that is popped from the bottom of the stack, possibly along with the
   contents of the network layer header itself (Section 2.2 of
   [RFC3032]).  Accordingly, the label initially pushed onto a network
   layer packet must be associated either with a single network layer
   protocol or with a specified set of protocols distinguishable by
   inspecting the network layer header.  Any label value that replaces
   this label in transit must satisfy the same criteria.

   In SR-MPLSv6, the ingress PE resolves an IPv4 route whose BGP next
   hop is the IPv6 loopback address of the egress PE [RFC8950], and
   imposes the Prefix-SID label that is bound to that IPv6 address.
   That label is therefore bound to an IPv6 prefix, but carries an IPv4
   packet and has the S bit [RFC3032] set.  Neither [RFC8660] nor the
   IGP extensions for Segment Routing [RFC8667] [RFC8666] state whether
   such a label may carry IPv4 packets, nor how a node that pops or
   swaps the label determines the network layer protocol of the packet
   beneath it.

2.2.  Penultimate Hop Popping

   When the Prefix-SID is advertised with the P-Flag (No-PHP) clear, the
   penultimate hop pops the corresponding label (Section 2.1.1.3 of
   [RFC8667]).  If this operation empties the label stack, forwarding
   the exposed packet to the ultimate hop requires the penultimate hop
   to identify its network layer protocol and select the appropriate
   link-layer protocol identifier, such as the EtherType [IANA-IEEE802]
   on an Ethernet link.

   In SR-MPLSv6, the exposed packet may be IPv4, while the outgoing
   interface is an IPv6-only IGP adjacency towards the ultimate hop.
   The IGP provides IPv6 reachability to the ultimate hop, but this does
   not by itself establish support for transmitting an unlabeled IPv4
   packet over the associated outgoing adjacency.

   The mechanisms specified for IS-IS [RFC5308], multi-topology IS-IS
   [RFC5120], and OSPFv3 address families [RFC5838] do not define IPv4
   routing through IPv6 next hops comparable to the capability provided
   by [RFC8950] for BGP, as discussed in Section 3.3 of
   [I-D.ietf-intarea-v4-via-v6].  Support for both address families
   within an IGP therefore does not imply support for IPv4-via-IPv6
   forwarding.

   PHP forwarding uses the next hop selected by the label lookup
   (Section 3.16 of [RFC3031]).  It therefore does not inherently
   require an IPv4 route to the packet's destination at the penultimate
   hop.  Nevertheless, the forwarding implementation must support
   transmitting the exposed IPv4 packet over the selected outgoing
   adjacency, even when the outgoing interface has only IPv6 addressing.
   If the implementation does not support this operation, the packet is
   discarded at the penultimate hop.

2.3.  Explicit NULL

   For IS-IS, when the Prefix-SID is advertised with both the P-Flag and
   the E-Flag set, the penultimate hop replaces the corresponding label
   with an Explicit NULL label, with a value of "0 for IPv4 and 2 for
   IPv6" (Sections 2.1 and 2.1.1.3 of [RFC8667]).  Section 6 of
   [RFC8666] specifies the corresponding behavior for OSPFv3.  These
   specifications do not explicitly state whether the value is selected
   according to the address family of the advertised prefix or according
   to the network layer protocol of the packet being forwarded.

   If the value is selected according to the address family of the
   prefix to which the Prefix-SID is bound, the IPv4 packet is sent to
   the ultimate hop with the IPv6 Explicit NULL label (2).  That label
   specifies that, after it is popped, forwarding is based on the IPv6
   header (Section 2.1 of [RFC3032]).  In the global routing context
   considered here, this directs the exposed IPv4 packet to IPv6
   processing rather than IPv4 processing.  The packet's Version field
   is inconsistent with the selected network layer protocol action.
   Therefore, an implementation that checks this field against the
   selected protocol action will discard the packet instead of
   incorrectly forwarding an IPv4 packet using the global IPv6
   forwarding table.

2.4.  Ultimate Hop Popping

   For IS-IS, when the Prefix-SID is advertised with the P-Flag set and
   the E-Flag clear, the penultimate hop forwards the packet to the
   ultimate hop with the label corresponding to that Prefix-SID at the
   ultimate hop (Section 2.1.1.3 of [RFC8667]).  Section 6 of [RFC8666]
   specifies the corresponding behavior for OSPFv3, using the NP-Flag
   set and the E-Flag clear.  The penultimate hop neither pops the label
   nor replaces it with an Explicit NULL label.

   In the SR-MPLSv6 case considered here, the ultimate hop is the egress
   PE, and the received label corresponds to its own Prefix-SID bound to
   an IPv6 prefix.  When this label has the S bit set, popping it
   exposes the network layer packet.  The action after popping depends
   on the instruction associated with the label and on the contents of
   the exposed packet (Section 2.10.2 of [RFC8660]).

   If the Label Forwarding Information Base (LFIB) entry for the Prefix-
   SID label selects IPv6 processing solely because the Prefix-SID is
   bound to an IPv6 prefix, popping the label directs the exposed IPv4
   packet to IPv6 processing in the global routing context.  As in
   Section 2.3, the packet's Version field is inconsistent with the
   selected network layer protocol action.  Therefore, an implementation
   that checks this field against the selected protocol action will
   discard the packet instead of incorrectly forwarding an IPv4 packet
   using the global IPv6 forwarding table.

2.5.  Existing Workarounds

   An ingress PE can avoid the ambiguity by imposing an additional
   bottom-of-stack label that identifies the packet as IPv4, analogous
   to the second level of labels used by 6PE (Section 3 of [RFC4798]).
   That label can be advertised by the egress PE using BGP-LU [RFC8277],
   as described in [I-D.mishra-idr-v4-islands-v6-core-4pe], and can be
   the IPv4 Explicit NULL label.

   This approach requires BGP-LU, or an equivalent mechanism, in
   addition to or instead of plain IPv4 unicast NLRI.  The additional
   label consumes one entry in the label stack solely to identify the
   payload as IPv4.  On hardware with limited label imposition capacity
   (see Maximum SID Depth [RFC8491]), this leaves fewer entries
   available for other labels and can restrict the segment lists that
   the ingress PE can impose.

2.6.  Unaffected Cases

   Services in which the bottom-of-stack label is a service label, such
   as BGP/MPLS IP VPNs [RFC4364] [RFC4659], are not affected by the
   ambiguity described above.  For such services, the Prefix-SID label
   is not at the bottom of the stack.  Removing it therefore leaves a
   labeled packet rather than exposing the network layer header.  The
   service label determines the subsequent forwarding treatment at the
   egress PE according to the applicable service procedures.

   IPv6 packets carried over a Prefix-SID bound to an IPv6 prefix are
   not affected either.

3.  Network Layer Awareness

   This section specifies procedures for network layer awareness in the
   SR-MPLS data plane.  In terms of Section 2.2 of [RFC3032], a Prefix-
   SID label that is bound to an IPv6 prefix in an SR-MPLSv6 deployment
   is used for the set of network layer protocols consisting of IPv4 and
   IPv6, and packets of the two protocols are distinguished by
   inspection of the network layer header as specified in Section 3.1.

   The procedures apply to packets that are forwarded using a Prefix-SID
   that is bound to an IPv6 prefix of the egress PE, and that carry no
   label beneath that Prefix-SID, i.e., the Prefix-SID label has the S
   bit set when it is popped or replaced.  Packets with additional
   labels beneath the Prefix-SID are processed as specified in [RFC8660]
   and are not affected by this document.

   Depending on the configuration of the Prefix-SID, i.e., the P-Flag
   and the E-Flag for IS-IS [RFC8667] or the NP-Flag and the E-Flag for
   OSPFv3 [RFC8666], the payload address family is determined by the
   penultimate hop (Sections 3.2 and 3.3) or by the ultimate hop
   (Section 3.4).

3.1.  Determining the Payload Address Family

   A node determines the payload address family by inspecting the
   Version field, i.e., the first four bits, of the network layer header
   that immediately follows the label stack entry with the S bit set.
   The value 4 indicates IPv4 [RFC791], and the value 6 indicates IPv6
   [RFC8200].

   If the Version field contains any other value, the node MUST NOT
   apply the procedures in this document, and MUST process the packet as
   it would in the absence of this document.

   Inspection of the first nibble beyond the label stack is already
   commonly performed by LSRs, e.g., for equal-cost multipath (ECMP)
   load balancing [RFC4928].

3.2.  Implicit NULL

   This procedure applies when the Prefix-SID of the ultimate hop is
   advertised with the P-Flag clear, i.e., when the penultimate hop pops
   the Prefix-SID.

   The ingress PE receives an IPv4 packet whose route resolves to the
   IPv6 /128 loopback address of the egress PE.  The ingress PE and the
   transit nodes apply the PUSH and CONTINUE operations as specified in
   [RFC8660], until the packet reaches the penultimate hop.

   When the penultimate hop pops the Prefix-SID and the label stack
   becomes empty, the penultimate hop MUST determine the payload address
   family as specified in Section 3.1.

   *  If the payload is IPv4, the penultimate hop MUST transmit the
      packet to the ultimate hop as an IPv4 packet.  On an Ethernet
      link, this means that the penultimate hop sets the EtherType to
      0x0800 and sends the frame to the link-layer address of the
      ultimate hop.

   *  If the payload is IPv6, the penultimate hop MUST transmit the
      packet to the ultimate hop as an IPv6 packet, e.g., with EtherType
      0x86DD on an Ethernet link.

   The ultimate hop thereby receives the packet with a link-layer
   protocol identifier that matches its network layer header, and
   processes it for further routing or switching like any other native
   IPv4 or IPv6 packet.

3.3.  Explicit NULL

   This procedure applies when the Prefix-SID of the ultimate hop is
   advertised with both the P-Flag and the E-Flag set, i.e., when the
   penultimate hop replaces the Prefix-SID with an Explicit NULL label
   (Section 2.1.1.3 of [RFC8667]).

   The ingress PE and the transit nodes behave as described in
   Section 3.2.  When the penultimate hop replaces a Prefix-SID label
   that has the S bit set with an Explicit NULL label, it MUST determine
   the payload address family as specified in Section 3.1, and MUST
   select the Explicit NULL label according to the payload address
   family rather than according to the address family of the prefix to
   which the Prefix-SID is bound:

   *  If the payload is IPv4, the penultimate hop MUST use the IPv4
      Explicit NULL label (0).

   *  If the payload is IPv6, the penultimate hop MUST use the IPv6
      Explicit NULL label (2).

   The penultimate hop then forwards the packet to the ultimate hop
   using the regular IGP forwarding procedures.  The ultimate hop
   thereby receives the packet with the Explicit NULL label that matches
   the payload, and processes the packet for further routing or
   switching in its global routing table as specified in [RFC3032].

3.4.  Ultimate Hop Popping

   This procedure applies when the Prefix-SID of the egress PE is
   advertised with the P-Flag set and the E-Flag clear for IS-IS
   (Section 2.1.1.3 of [RFC8667]), or with the NP-Flag set and the
   E-Flag clear for OSPFv3 (Section 6 of [RFC8666]).  The egress PE is
   the ultimate hop and terminates the Prefix-SID bound to its own IPv6
   prefix.

   The ingress PE and the transit nodes apply the PUSH and CONTINUE
   operations as specified in [RFC8660].  The penultimate hop forwards
   the packet with the label corresponding to the Prefix-SID at the
   ultimate hop, without popping it or replacing it with an Explicit
   NULL label.

   When the ultimate hop pops the Prefix-SID label and the label stack
   becomes empty, it MUST determine the payload address family as
   specified in Section 3.1.  It MUST select the subsequent network
   layer processing according to the payload address family rather than
   the address family of the prefix to which the Prefix-SID is bound:

   *  If the payload is IPv4, the ultimate hop MUST process the exposed
      packet as IPv4 and use its global IPv4 forwarding table for any
      subsequent IP forwarding lookup.

   *  If the payload is IPv6, the ultimate hop MUST process the exposed
      packet as IPv6 and use its global IPv6 forwarding table for any
      subsequent IP forwarding lookup.

   These requirements specify the network layer processing associated
   with the NEXT operation described in Section 2.10.2 of [RFC8660] for
   the SR-MPLSv6 case considered here.

3.5.  First Hop and Ultimate Hop

   The first hop knows the address family of each packet that it
   receives from a CE.  When the first hop and the ultimate hop are
   adjacent, the first hop is also the penultimate hop.  It uses the
   payload address family already determined at ingress and forwards the
   packet according to the applicable procedure in Sections 3.2, 3.3, or
   3.4:

   *  For Implicit NULL (Section 3.2), the first hop transmits the
      packet without an MPLS label and with the link-layer protocol
      identifier corresponding to the payload address family.

   *  For Explicit NULL (Section 3.3), the first hop imposes only the
      Explicit NULL label corresponding to the payload address family:
      label 0 for IPv4 or label 2 for IPv6.

   *  For Ultimate Hop Popping (Section 3.4), the first hop imposes the
      label corresponding to the egress PE's Prefix-SID and sends the
      labeled packet directly to it.  The egress PE pops the label and
      processes the exposed packet as specified in Section 3.4.

4.  Traffic Engineering Router ID

   Every SR-MPLSv6 node MUST support the use of a stable, routable IPv6
   address as its sole Traffic Engineering (TE) Router ID.  For IS-IS,
   the IPv6 TE Router ID TLV is specified in Section 4.1 of [RFC6119].
   For OSPFv3, the Router IPv6 Address TLV is specified in Section 3 of
   [RFC5329].  The address-selection and advertisement rules of the
   corresponding specification apply.

   An SR-MPLSv6 node MUST support operation of its implemented TE
   functions using IPv6 TE Router IDs and IPv6-only infrastructure
   addressing within the SR-MPLSv6 domain, including when steering IPv4
   traffic.  This requirement applies to SR Policy-based traffic
   engineering [RFC9256], BGP Egress Peer Engineering (EPE) [RFC9087],
   and other TE functions supported by the node in its role.  Any IP-
   based control-plane communication required by those functions within
   the domain MUST support IPv6-only control plane.  These requirements
   do not mandate that every node implement every TE function.

   The address family of the traffic being steered is independent of the
   address family used for TE identification and infrastructure
   addressing.  Section 2.1 of [RFC9256] permits IPv6 addresses to
   identify SR Policy headends and endpoints.  Section 8.4 specifies
   service-route steering for both IPv4 and IPv6 traffic over SR-MPLS
   and SRv6.

   SRv6 provides a corresponding example of IPv4 service delivery over
   IPv6 infrastructure.  Section 5 of [RFC9252] specifies IPv6 BGP next
   hops and steering into SRv6 Policies; Sections 5.1 and 5.3 cover IPv4
   VPN and global IPv4 services, respectively.  Section 5.1 of [RFC8986]
   specifies encapsulation of IPv4 traffic into an SRv6 Policy, and
   Section 4.7 specifies decapsulation and lookup in an IPv4 forwarding
   table.

   The IPv6 TE Router ID is distinct from the OSPFv3 Router ID and the
   BGP Identifier.  Those protocol fields retain their existing formats
   and semantics.  The OSPFv3 Router ID is a 32-bit value that can be
   assigned administratively (Appendix C.1 of [RFC5340]); the BGP
   Identifier is a four-octet, unsigned, non-zero integer (Section 2.1
   of [RFC6286]).  Neither requires an IPv4 interface address.

   NLRI carried as specified in [RFC8950].  The addressing and protocols

6.  Operational Considerations

6.1.  Deployment

   The procedures in Section 3.2 and Section 3.3 are performed by the
   penultimate hop, which is not the node that imposes the Prefix-SID.
   A first hop therefore cannot, by itself, ensure that IPv4 packets are
   delivered correctly.  For these procedures, every node that can act
   as the penultimate hop for the Prefix-SID of an egress PE, including
   nodes on ECMP paths and on fast-reroute repair paths, needs to
   implement this document.  In Figure 2, for example, PE4 becomes the
   penultimate hop for traffic to PE3 if both links between PE3 and the
   P routers fail.

   In a network in which some nodes do not implement this document, IPv4
   traffic can be discarded.  For the procedures in Sections 3.2 and
   3.3, operators can avoid this by ensuring that all potential
   penultimate hops implement this document before carrying IPv4 traffic
   without an additional label, or by continuing to use one of the
   approaches described in Section 2.5 towards egress PEs for which this
   cannot be ensured.

   For the procedure in Section 3.4, the egress PE needs to support
   network layer identification and processing at the ultimate hop.

6.2.  IPv4 Forwarding over IPv6-Only Links

   With the procedure in Section 3.2, the ultimate hop receives native
   IPv4 packets on core-facing interfaces that have no IPv4 address.
   The penultimate hop resolves the link-layer address of the ultimate
   hop using IPv6 Neighbor Discovery [RFC4861], so neither an IPv4
   address nor ARP is needed on the link.  The ultimate hop, however,
   needs to accept and process IPv4 packets received on such interfaces;
   implementations that discard IPv4 packets received on interfaces on
   which IPv4 is not enabled need IPv4 processing to be enabled on the
   core-facing interfaces of the ultimate hop.

6.3.  Label Stack Depth

   Compared to the approaches described in Section 2.5, the procedures
   in this document carry IPv4 packets with one label fewer.  This is
   beneficial where the Maximum SID Depth [RFC8491] of the ingress PE
   limits the number of labels that can be imposed.

6.4.  Equal-Cost Multipath

   Transit nodes commonly inspect the first nibble beyond the label
   stack to select among ECMP paths [RFC4928].  This document does not
   change that behavior.  As noted in Section 5, behavior in both the
   ECMP and the non-ECMP cases needs verification.

   When Entropy Labels [RFC6790] are used, the Prefix-SID is not at the
   bottom of the label stack.  A penultimate hop may, however, pop the
   Entropy Label Indicator and the Entropy Label in addition to the
   Prefix-SID (Section 4.4 of [RFC6790]), which exposes the payload in
   the same way as described in Section 2.2.  The interaction of this
   document with Entropy Labels is an open issue (Appendix A).

6.5.  Operations, Administration, and Maintenance

   LSRs that run IPv6 only cannot generate ICMPv4 messages for IPv4
   packets whose TTL expires within the SR-MPLS domain (Section 3.4.1 of
   [RFC7439]); this document does not address that gap.  LSP Ping and
   Traceroute for SR-MPLS [RFC8287] validate the Prefix-SID itself, but
   do not exercise the procedures in this document; operators may need
   to complement them with end-to-end IPv4 probes.

7.  IANA Considerations

   This document has no IANA actions.

8.  Security Considerations

   This document does not introduce any new control plane messages or
   extensions, and the security considerations of [RFC8402], [RFC8660],
   and [RFC8667] apply.

   Section 8.1 of [RFC8402] notes that SR does not introduce any new
   behavior in the MPLS data plane.  This document does introduce a data
   plane behavior: the penultimate hop, and in some cases the ultimate
   hop, inspects the first four bits of the network layer header that
   follows the label stack entry with the S bit set.  That inspection is
   at a fixed offset and of a fixed size, and is comparable to the
   inspection that LSRs already perform for ECMP [RFC4928].  Packets
   whose Version field is neither 4 nor 6 are processed as they would be
   in the absence of this document.

   The procedures allow IPv4 packets that carry only a Prefix-SID to be
   delivered into the global routing table of the egress PE.  This is
   not a new capability: a node that can inject labeled packets into the
   SR domain can already achieve the same result by imposing an IPv4
   Explicit NULL label beneath the Prefix-SID.  As with any SR-MPLS
   deployment, SR domain boundary routers are required to filter
   external traffic destined to labels associated with segments within
   the trusted domain (Section 8.1 of [RFC8402]).

Appendix A.  Open Issues

   This section is to be removed before publishing as an RFC.

   The following issues are open and are to be resolved in future
   revisions of this document:

   1.  Whether this document updates [RFC8660], [RFC8667], and [RFC8666]
       with respect to the selection of the Explicit NULL label value
       (Section 3.3).

   2.  Whether a capability advertisement is needed so that an ingress
       PE can determine that the penultimate hops towards an egress PE
       implement this document (Section 6.1); such an advertisement
       would require IANA actions.

   3.  Completion of the procedures for the first hop and the ultimate
       hop (Section 3.5).

   4.  Verification of behavior in both the ECMP and the non-ECMP cases
       of the example topologies (Section 5).

   5.  Interaction with Entropy Labels [RFC6790], including a
       penultimate hop that pops the Entropy Label along with the
       Prefix-SID (Section 6.4), and with fast-reroute repair paths.

   6.  Whether the procedures should also apply to IPv6 payloads carried
       over Prefix-SIDs bound to IPv4 prefixes, and to IPv6-signaled LDP
       LSPs [RFC7552].

   7.  Whether the procedures are enabled by default or only by
       configuration.
